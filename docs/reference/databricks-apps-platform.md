# Databricks Apps platform — what it gives and what it limits

What the vendor docs say (and leave out) about the Apps platform — the container, the request path, identities, storage, packages and `app.yaml` — plus what the spikes measured. [Platform at a glance](#platform-at-a-glance) is the one-page summary; the sections below hold the detail. Written so nobody researches it twice. Sources were read on 2026-10-29; re-read before relying on a detail, the platform changes.

## Platform at a glance

One row per thing the platform decides for appmux. **Measured** rows come from the spikes of 2026-10-29 and 2026-10-30 on a **Free Edition** container; a paid workspace may differ ([TD-005](../tech-debt.md#td-005-platform-measurements-come-from-free-edition-only)). Documented rows say so. Detail for each row is in the linked section.

| Area | What the platform does | What appmux does about it |
|---|---|---|
| Container | Userland Ubuntu 22.04 (documented) on a 6.1.188 Amazon Linux 2023 kernel; uid 1000, no root; Python 3.11.17, Node 22, gcc; 8 GiB of memory, 4 CPUs visible but a quota of about 2 ([container table](databricks-free-edition.md#measured-on-the-container-2026-10-29)) | One container hosts every child; admission control budgets the 8 GiB; CPU is the unguarded resource ([TD-003](../tech-debt.md#td-003-cpu-and-memory-limits-are-best-effort)) |
| Privileges | Unprivileged user, mount, net, pid and ipc namespaces work; no `/dev/net/tun`; cgroup and `oom_score_adj` writes are denied; `ptrace_scope` 0 | Sandbox from namespaces ([ADR 0003](../decisions/0003-isolate-children-with-unprivileged-namespaces-and-a-filtering-pump.md)); egress pump on a veth pair; only rlimits and a CPU pin limit a child |
| Same-uid exposure | A same-uid process reads platform secrets and `environ` of every process, and writes the app directory, `/home/app` and `/dev/shm` ([filesystem table](databricks-free-edition.md#filesystem-seen-by-a-same-uid-process-spike-2-2026-10-30)) | The child's root is built from an allow-list; `self_check()` proves 18 canaries |
| Process 1 | `lha-runtime` does not reap orphans | The launcher is a subreaper |
| Request path | Reverse proxy, HTTP/1.1 to the app, 300 s per request or stream, 32 KB per header, no body limit up to 100 MB, paths normalised, identity headers overwritten, WebSocket works ([request path](#request-path)) | The edge trusts the forwarded identity, reads the client address from `X-Real-Ip`, and keeps its own timeouts below 300 s |
| Identity | Each App has its own service principal; with user authorization on, the proxy adds `X-Forwarded-Access-Token`; scopes are per App and reach tokens only after a stop and start ([identities](#identities-and-who-may-grant)) | appmux's SP is the shared identity; a child gets a token only through delegation ([ADR 0011](../decisions/0011-gate-credentials-and-platform-fields-behind-a-request-catalogue.md)) |
| Permissions | `CAN USE` and `CAN MANAGE`; a change shows after 1.5–6 min; nested groups after 60–75 s; SCIM `/Me` includes nested groups | `authorize()` mirrors the two levels; group cache 300 s ([ADR 0010](../decisions/0010-mirror-databricks-permissions-and-give-platform-admins-implicit-access.md)) |
| Lakebase | Checks a token only at login and ignores its scopes; one project on Free Edition | Split writers; the OBO residual is accepted ([ADR 0004](../decisions/0004-keep-decisions-in-a-nine-table-lakebase-registry-with-split-writers.md), [TD-002](../tech-debt.md#td-002-an-obo-childs-token-reaches-the-registry)) |
| Secrets | An App's SP with `READ` on a scope reads values by REST and SDK | A secret is a `scope/key` reference read at child start ([ADR 0009](../decisions/0009-attach-resources-with-the-attachers-own-token-and-reference-secrets.md)) |
| Storage | `/tmp` survives a redeploy and is emptied by a stop and start; writes to the app directory do not persist; an SP writes workspace files up to 500 MB each | Content store in the SP's workspace folder; caches in `/tmp` are rebuilt after a stop ([ADR 0005](../decisions/0005-run-releases-from-immutable-snapshots-and-swap-after-health.md)) |
| Packages | The environment has 132 packages (for example `fastapi 0.115.0`, `uvicorn 0.30.6`, `starlette 0.38.6`); the platform runs `pip -r requirements.txt` and honours `--no-index --find-links` ([app environment](#app-environment-and-appyaml)) | The environment is every child's base layer; wheels go into a read-only overlay; appmux's own dependencies are vendored ([ADR 0007](../decisions/0007-resolve-packages-environment-first-with-a-wheel-overlay.md), [ADR 0014](../decisions/0014-build-the-edge-on-the-environments-http-stack.md)) |
| `app.yaml` | Two keys; `$NAME` is substituted in `command` only; a `valueFrom` with no resource only logs an error | appmux copies the substitution and fails the release instead ([ADR 0008](../decisions/0008-follow-the-standalone-app-yaml-contract.md)) |
| Lifecycle | 15 s between `SIGTERM` and `SIGKILL`; Free Edition adds 3 apps per account and an auto-stop after 24 h ([limits](databricks-free-edition.md#documented-limits)) | Drain within 15 s; the daily restart exercises the start path |

Not measured: a paid workspace (CPU quota, pod network, container size), the capacity of the real edge, memory-hog and CPU-fairness behaviour inside the pinned CPU. The list is kept in the [spikes log](../../specs/001-appmux-v1/spikes/README.md) and the [debt log](../tech-debt.md).

## Request path

**Documented**
- Requests reach the app through a reverse proxy, so "your app can't depend on the origin of requests". Databricks terminates TLS; the app must not.
- Apps must support HTTP/2 cleartext (H2C), listen on `0.0.0.0` and use the port in `DATABRICKS_APP_PORT`.
- After `SIGTERM` the app has 15 seconds to exit before `SIGKILL`.
- Headers the proxy passes: `X-Forwarded-Host`, `X-Forwarded-Preferred-Username`, `X-Forwarded-User`, `X-Forwarded-Email`, `X-Real-Ip`, `X-Request-Id` (only when running inside Databricks Apps). The user-authorization token header is covered on the authorization page.
- Limit: 100 apps per workspace (fixed).

**Not stated in any page read** (measured since in spike 8, below; the rest is still unknown): custom domains or wildcard hostnames, and health checks. The pages are silent on base paths and URL prefixes, the original request path, whether the raw `Host` is forwarded, WebSocket and streaming support, request and response timeouts, body and header size limits, cookie handling, and whether client-supplied `X-Forwarded-*` headers are overwritten.

**Measured (probe on Free Edition, 2026-10-29)**
- All 9 request lines the app logged for proxied browser requests came from `127.0.0.1`: the platform proxy reaches the app from loopback, not from another address. The same requests were HTTP/1.1 and a plain `http.server` handled them (browser GETs only; H2C was not exercised).
- The app URL has the form `<app-name>-<id>.<region>.databricksapps.com`.

**Measured (spike 8, Free Edition, 2026-10-30; details in [the spike log](../../specs/001-appmux-v1/spikes/README.md#spike-8--behaviour-of-the-databricks-proxy-2026-10-30))**
- The proxy forwards the full path and query unchanged (no prefix stripping) but **normalises first**: `..` and `%2e%2e` segments are resolved, `//` gets a 301 to the single-slash path, `%2F` stays encoded.
- It speaks **HTTP/1.1** to the app, including to a server that supports H2C (no H2C request arrived); the client side is TLS.
- **300 s** is the ceiling for a request or a stream (504 `upstream request timeout`; an SSE stream is closed cleanly at the limit). WebSocket works and an idle connection survived 330 s.
- No body limit up to 100 MB in either direction (about 10 MB/s). A single header of 32 KB passes; 64 KB fails (431 for a request, 503 for a response).
- `Set-Cookie` and a relative `Location` pass through unchanged; the proxy adds its own `__Host-databricks-app-router` cookie.
- Client-supplied `X-Forwarded-Email`, `-User`, `-Access-Token`, `-Host`, `X-Real-Ip` and `X-Databricks-Org-Id` are **overwritten**; a client `X-Forwarded-For` value is kept as the leftmost entry and the proxy appends. `Authorization` is not forwarded; `Cookie` is.
- The CLI's OAuth token works as `Authorization: Bearer` and yields `X-Forwarded-Email` plus a proxy-minted `X-Forwarded-Access-Token`; without a valid bearer the answer is a 302 to the OIDC page when the request has no `Accept` header (or accepts `text/html`), and a 401 with the body `{}` when it accepts `application/json` ([measured 2026-11-03](mcp-and-a2a.md#what-each-failure-looks-like)).

## Identities and who may grant

- Every Databricks App gets its own service principal automatically ("Databricks automatically provisions a dedicated service principal for the app"). It cannot be reused across apps and is deleted with the app. Creating an app is not documented as an admin action.
- A child inside appmux is not a Databricks App, so it has no such SP. Keeping a Databricks App per child only for its SP would spend the slots appmux exists to save.
- Adding a service principal to a workspace is documented as a workspace-admin action (account admins add them to the account). The docs do not say who may read or create an OAuth secret for an app's SP; they say only that `DATABRICKS_CLIENT_ID` and `DATABRICKS_CLIENT_SECRET` are injected into the app's environment.
- Resources: "Grant the service principal access to specific resources using standard permission assignments"; the docs do not say grants are automatic or who must hold what to add a resource.
- Unity Catalog privileges are granted by the object's owner, the owner of the catalog or schema containing it, a holder of `MANAGE`, or a metastore admin. A workspace admin gets grant power only through owning the workspace catalog.
- OAuth scopes: workspace admins control which scopes app developers may add (an allowlist); account admins can add scopes outside it. Scopes are set per app, so every user-authorized child of appmux receives tokens carrying the same scope set.
- Lakebase: the project owner grants `CAN MANAGE`; creating an OAuth role for a service principal is in the Lakebase docs, which do not state that a workspace admin is needed.
- Apps permissions (read 2026-10-30): `CAN USE` and `CAN MANAGE` (the latter includes `CAN USE` and may edit, delete and assign permissions); grantees are users, groups, service principals and "Anyone in my organization can use".
- Secrets (checked 2026-10-30): an App receives a secret by having it as a resource, injected into that App's environment through `valueFrom`; the permission is set per secret scope, not per key. The value-returning Secrets API call (`get-secret`) is documented as callable only through the `DBUtils` interface; measured on Free Edition (spike 11) it is not: an App's service principal, not a workspace admin, reads a value with `READ` on the scope through REST `GET /api/2.0/secrets/get` and through the SDK (`dbutils.secrets.get`, `secrets.get_secret`). A user's OBO token cannot call the Secrets API: it needs the scope `secrets`, which `user_api_scopes` does not accept, but `SELECT length(secret('scope', 'key'))` on a SQL warehouse runs as that user with the `sql` scope and succeeds only with `READ`. A grant takes effect at once; a revoked `READ` kept working for minutes. The SP could create its own scope. The v1 design attaches a `secret` as a reference (`scope/key`) and reads the value with the appmux SP when the child starts ([design §8.3](../product/v1-design.md#83-secrets-where-the-value-comes-from)).
- Resources (checked 2026-10-30): the resources page lists 14 types, secret among them. The 13 others, with their permission levels and the value `valueFrom` yields, are mirrored in [v1-data-model.md §4.7](../product/v1-data-model.md#47-app_resources); appmux's own `secret` type is a `scope/key` reference to a Databricks scope. To add a resource, the user needs `Can manage` on the resource and on the app. The docs do not describe a per-resource attach check beyond that; the v1 design makes its own, with the attacher's token ([design §8.2](../product/v1-design.md#82-resources-and-env-entries)).
- OBO scopes (checked 2026-10-30): the default scopes are `iam.access-control:read` and `iam.current-user:read`; others the pages list include `sql`, `files`, `postgres`, `catalog.*` and `workspace.workspace`, in `:read` and write forms; workspace admins manage the allowlist. A change of an app's `user_api_scopes` reaches the tokens only after the app is stopped and started (spike 1); Lakebase accepts a valid token whatever its scopes (spike 1). Names `user_api_scopes` accepts (spikes 15 and 16): the coarse `sql`, `apps`, `genie`, `model-serving`, `vector-search`, `files`, `ai-gateway`, and the fine-grained `workspace.workspace` and `:read`, `files.files(:read)`, `serving.serving-endpoints(:read)`, `catalog.catalogs:read`, `catalog.schemas(:read)`, `catalog.tables(:read)`, `catalog.connections(:read)`, `vectorsearch.vector-search-indexes:read`, `dashboards.genie(:read)` and `postgres`; it refuses `secrets`, `mlflow`, `jobs`, `access-management`, `workspace`, `unity-catalog` and `catalog.volumes`. `workspace.workspace:read` is enough to get the status of, list and export a folder as the user and not to write; the workspace API answers a caller with no access with an empty listing or a 404, not an error. A token with no matching scope gets HTTP 403 `Invalid scope, required scopes: <name>`, which names the scope the call needs.
- Resource pickers (written 2026-11-04; **shapes and the fallback measured on the dev App with a CLI token; a browser session's token not measured**): the Add resource form lists the objects of all 14 types (`admin/resource_suggestions.py`; calls and targets in [admin-api.md](../../specs/001-appmux-v1/contracts/admin-api.md#resourcesuggestionlist)). The answer shapes the code reads (field names and counts only, no names) were read with the Databricks CLI's token on the Free Edition workspace for the Unity Catalog levels (catalogs, schemas, tables, volumes, functions), connections, Genie spaces, apps, vector search, Lakebase Autoscaling projects and Provisioned instances. The model-services path was a guess that the dev App's answer on 2026-11-04 confirmed; the CLI token is a user's, so this says nothing about an App's tokens. The scope each call needs is taken from the REST reference and the names above, not measured with an App token: `catalog.catalogs:read`, `catalog.schemas:read` and `catalog.tables:read` for tables, `catalog.connections:read`, `dashboards.genie:read`, `vectorsearch.vector-search-indexes:read`, `apps`, `postgres`, `serving.serving-endpoints:read` and `sql` are in the accepted list; functions need `unity-catalog` and volumes need `catalog.volumes`, secrets, MLflow and jobs need `secrets`, `mlflow` and `jobs`, none of which `user_api_scopes` accepts, so for those five the picker retries with appmux's own service-principal token (`source: "platform_token"`), which shows what appmux can read and not what the person can. Undocumented: the scope of `GET /api/2.1/unity-catalog/model-services` (gateway model services; Free Edition has none) and of `GET /api/2.0/database/instances` (Lakebase Provisioned). On 2026-11-04 the dev App answered the Databricks CLI's token (a user's token sent to the App; a browser session's token was not tried) for all 14 types: `sql_warehouse`, `serving_endpoint`, `uc_connection` and `genie_space` were listed with that token (`source: "caller_token"`), and the other ten were refused it and read again with appmux's own service-principal token (`source: "platform_token"`): `secret`, `mlflow_experiment`, `job`, `vector_search_index`, `lakebase_database`, `databricks_app`, `gateway_model_service` and the three Unity Catalog types `uc_table`, `uc_volume` and `uc_function`. The documented scopes predicted five of those ten, so a scope the App declares in `user_api_scopes` is what decides, not the list of names Databricks accepts (the cause was not checked type by type). With appmux's token the levels of Unity Catalog (catalogs, then schemas, then objects, for tables, volumes and functions), of a Lakebase project (project, then branch) and the model services all answered with entries; secrets, MLflow experiments, jobs and vector search endpoints answered with none, which says that appmux's service principal sees nothing of those kinds, not that nothing exists. A catalog or secret scope that does not exist answers `platform_token`, no items and a note that it is not visible to appmux. The dev App then declared five more scopes (`catalog.catalogs:read`, `catalog.schemas:read`, `vectorsearch.vector-search-indexes:read`, `apps`, `postgres`), was stopped and started, and the same call listed nine types with the CLI token: Lakebase, apps and the first level of the three Unity Catalog types joined the four above (the volume and function levels under a schema were not measured). Five still fell back: `secret`, `mlflow_experiment` and `job` (their scopes are refused to an App), `gateway_model_service` (no scope is documented) and `vector_search_index` (cause not found; the scope added covers the index list, not necessarily the endpoint list). Attaching a secret that does not exist, with `attach_check_warehouse_id` set to the dev workspace's only warehouse, answered `400 no_access` ("you do not have READ on secret scope"); with the setting unset it is refused as `check_warehouse_unset` before any statement is sent, whether or not the secret exists. To measure with a browser session's token, as a non-admin who manages an app, call `GET /_appmux/api/v1/resources/suggestions?type=secret` and read `source`.
- Runtime detection (checked 2026-10-30): the deployment logic looks for `package.json` (Node), `requirements.txt`, or `pyproject.toml` together with `uv.lock` (Python), and runs the `command` in `app.yaml` when there is one. appmux copies this detection instead of asking for an `app_type`.
- Groups (checked 2026-10-30): the SCIM current-user endpoint (`GET /api/2.0/preview/scim/v2/Me`) returns a `groups` list for the caller. The pages read do not say whether groups reached through nesting are included: spike 12.
- Folder browser (**measured on the dev App 2026-11-05 with the CLI token; a browser session's token not tried**, T194): `GET /workspace/browse` listed the roots (no upstream call), `/Workspace` (3 folders and 1 file) and three fixture folders with the person's token and the scope `workspace.workspace:read` the dev App declares, and `markers`, `looks_like_app`, `runtime_hint` and `suggested_memory_mb` read as the contract says: a folder with `app.yaml` and `requirements.txt` gave `looks_like_app` true, `runtime_hint` `python` and `suggested_memory_mb` null; a folder with only `package.json` gave `node` and 768; `/Workspace` gave no markers and a null hint. Run again the same day, the resource pickers answered as in the paragraph above: nine types with `source: "caller_token"`, and `secret`, `mlflow_experiment`, `job`, `vector_search_index` and `gateway_model_service` with `platform_token` and no items (T195).
- Directory reads for the Sharing form (**measured on the dev App 2026-11-05**, T187): `GET /principals` lists SCIM `Users`, `Groups` and `ServicePrincipals` (`GET /api/2.0/preview/scim/v2/<kind>?filter=<field> co "<q>"&count=<n>`; the installed SDK documents `co` and `or` for `filter`) with the visitor's token first. **The default scopes do not cover it.** Through the Apps proxy, with the dev App's `user_api_scopes` (the default identity scopes plus `workspace.workspace:read`, `sql`, `files.files:read`, the `catalog.*` reads, `dashboards.genie:read`, `serving.serving-endpoints:read`, `vectorsearch.vector-search-indexes:read`, `apps` and `postgres`), the visitor's token was refused with `403` on all three directories, and the body said `Provided OAuth token does not have required scopes: scim`. The scope the call needs is therefore `scim`; whether `user_api_scopes` accepts that name was not tried (some coarse names are refused, see [design §13](../product/v1-design.md#13-deployment-and-operations)), so the workspace's scope allowlist and a stop and start of the App may be part of adding it. When the visitor's token is refused, appmux asks again with its own service principal's token, and that one listed users, groups and service principals on the dev App (whether that needs the service principal to hold more than an ordinary App's rights is not measured): every call of the probe, five in all (`q=a` for all three kinds, each kind alone, and `q=everyone`), answered `200` with `sources` equal to `platform_token` for each directory it read. So the Sharing form works on a deployment that never adds `scim`, but it reads the directory as appmux and not as the person. To see `caller_token`: add `scim` to `user_api_scopes`, stop and start the App, and call `GET /_appmux/api/v1/principals?q=a` again.

## App environment and `app.yaml`

Sources: [System environment](https://docs.databricks.com/aws/en/dev-tools/databricks-apps/system-env), read 2026-10-30.

- `app.yaml` has two keys, `command` and `env`. An `env` entry has a `name` and either a `value` or a `valueFrom` that names a resource key; resources are declared outside the file. The default resource keys the pages show are `app`, `genie-space`, `job`, `experiment`, `model`, `secret`, `sql-warehouse`, `connection`, `table`, `function`, `volume`, `vector-search-index` and `postgres`/`database`.
- Variables set in every app: `DATABRICKS_APP_NAME`, `DATABRICKS_WORKSPACE_ID`, `DATABRICKS_HOST`, `DATABRICKS_APP_PORT` ("the network port the app should listen on"; the page gives no value), `DATABRICKS_CLIENT_ID` and `DATABRICKS_CLIENT_SECRET`. The `OTEL_*` variables are set only when telemetry is enabled.
- Framework variables the runtime sets, with every port variable equal to `DATABRICKS_APP_PORT`: Gradio `GRADIO_SERVER_PORT` and `GRADIO_SERVER_NAME=0.0.0.0`; Streamlit `STREAMLIT_SERVER_PORT` and `STREAMLIT_SERVER_ADDRESS=0.0.0.0`; FastAPI and Uvicorn `UVICORN_PORT` and `UVICORN_HOST=0.0.0.0`; Flask `FLASK_RUN_PORT` and `FLASK_RUN_HOST=0.0.0.0`; `PORT` for Dash and Express; plus `STREAMLIT_SERVER_HEADLESS=true` and `STREAMLIT_BROWSER_GATHER_USAGE_STATS=false`.
- Runtime: Ubuntu 22.04, Python 3.11 in a dedicated virtual environment (apps that use `uv` can specify a different Python version), uv 0.10.2, Node.js 22; by default 2 vCPUs and 6 GB of memory per app.
- Packages: the page lists no pre-installed Python packages; an App's own Environment tab shows what its environment has. appmux treats the parent's environment as the base layer of every child's packages, with wheels installed into a per-release overlay on top (spike 18, [design §5.3](../product/v1-design.md#53-build-and-package-sources)).
- Measured (spike 17, Free Edition, 2026-10-30; [spike log](../../specs/001-appmux-v1/spikes/README.md#spike-17--appyaml-on-the-real-platform-2026-10-30)): `$DATABRICKS_APP_PORT` **is** substituted in a `command` argument and `${DATABRICKS_APP_PORT}` is **not**; neither is substituted in an `env` `value`. A `valueFrom` naming no resource logs a build `[ERROR]` but the deployment still starts, with the variable absent. The variables set also include `DATABRICKS_APP_URL`, `HOME=/home/app`, `LC_CTYPE=C.UTF-8`, `PYTHONUNBUFFERED=1`, `UV_PYTHON_INSTALL_DIR=/app/.uv-python`, `GRADIO_ANALYTICS_ENABLED=false`, `STREAMLIT_SERVER_ENABLE_CORS=false` and `STREAMLIT_SERVER_ENABLE_XSRF_PROTECTION=false`. The app is started as `python app.py` on `/usr/bin/python3.11` with `PATH=/usr/local/bin:/usr/bin:/bin:.venv/bin:node_modules/.bin`; plain `python3` is 3.10.12. The v1 contract is in [design §5.4](../product/v1-design.md#54-appyaml-requirements-and-start).

## Bundle (`databricks.yml`) app resources

Sources: [Bundle resources](https://docs.databricks.com/aws/en/dev-tools/bundles/resources), the `apps` entry, read 2026-10-30.

- An app is declared under `resources.apps.<key>` with `name`, `description`, `source_code_path`, `config` (`command`, `env`), `resources`, `permissions`, `user_api_scopes`, and compute, budget and git settings.
- Each item of `resources` has a `name`, an optional `description` and one type key: `secret` (`scope`, `key`, `permission` `READ`/`WRITE`/`MANAGE`), `sql_warehouse` (`id`, `permission` `CAN_USE`/`CAN_MANAGE`/`IS_OWNER`), `job` (`id`, `permission`), `serving_endpoint` (`name`, `permission` `CAN_QUERY`/`CAN_MANAGE`/`CAN_VIEW`), `experiment` (`experiment_id`, `permission` `CAN_READ`/`CAN_EDIT`/`CAN_MANAGE`), `genie_space` (`name`, `space_id`, `permission`), `database` (`database_name`, `instance_name`, `permission` `CAN_CONNECT_AND_CREATE`), `postgres` (`branch`, `database`, `permission`), `uc_securable` (`securable_type` `VOLUME`/`TABLE`/`FUNCTION`/`CONNECTION`/`MODEL_SERVICE`, `securable_full_name`, `permission`) and `app`. `app.yaml` refers to the item by its `name` through `valueFrom`.
- appmux reads only `resources.apps.<key>.resources[]` from a source's `databricks.yml` and offers those items in the Requirements panel; the mapping to appmux's resource types is in [v1-data-model.md §4.7](../product/v1-data-model.md#47-app_resources). Nothing is attached until the app admin confirms, and the attach check runs with the attacher's own token.

## What it means for appmux

- The edge cannot use the source address to tell the platform proxy from anything else: both are loopback. Identity headers are trusted only because nothing but the proxy can reach the edge's port, which `self_check()` proves for children.
- The proxy overwrites client-supplied identity headers (spike 8), so the edge may trust them. It must read the client address from `X-Real-Ip`, which the proxy overwrites. `X-Forwarded-For` is appended to (`<client-supplied>,<real client>,<hop>,<hop>`), so neither its leftmost entry (client-controlled) nor its rightmost (a proxy hop) is the client. Corrected 2026-10-30: the first wave of T022 had read "rightmost" from the spike 8 consequence below.
- The proxy speaks HTTP/1.1 to the app; the edge's HTTP library must accept HTTP/1.1, and H2C is optional (the docs ask for it; nothing was observed using it). The edge is built on uvicorn, Starlette and httpx, which the environment already ships ([ADR 0014](../decisions/0014-build-the-edge-on-the-environments-http-stack.md)).
- appmux has 15 seconds after `SIGTERM` to stop accepting, flush metrics and stop children; stop children in parallel.
- Routing design must not rely on any of the unstated behaviours above until measured.
