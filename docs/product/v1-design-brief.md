# appmux v1 — design brief (2026-10-29, updated 2026-10-30)

Output of a design session: the decision record (goal, constraints, alternatives, success criteria, spikes). What appmux v1 is and how it behaves is described in [v1-design.md](v1-design.md). Decisions here feed the first Spec Kit feature and the ADRs listed under [Hand-off](#hand-off). Nothing in this file is implemented; [ARCHITECTURE.md](../../ARCHITECTURE.md) marks what exists.

**Goal** — A platform team hosts up to ~100 registered child Databricks Apps behind one Databricks App slot, adds or updates a child from an admin panel without interrupting the others, and treats every child as potentially malicious.

## Users and pain

- **Platform admin** registers apps (directly, or by approving a visitor's request for one), sets each app's egress rules, answers requests (to register an app, to pass a credential down, or to change an app's name, slug, source folder or memory budget) and holds `CAN_MANAGE` on every app implicitly (user, 2026-10-30, round 8). **App admin** updates their app, manages its access and health check, and asks a platform admin for those credentials and changes. **User** sees a launcher with the apps they may open and can ask for a new one. Platform admin and app admin are each a person or a group: a platform admin is listed in the `platform_admins` setting, an app admin holds `CAN_MANAGE` on the app in appmux's grants; users hold `CAN_USE` (user, 2026-10-30).
- Pain: the workspace cap of 100 apps; in practice the team runs out of app slots (user's paraphrased answer).
- Pain: with a Databricks deployment in `AUTO_SYNC` mode, editing the source folder can break the running app (the user's observation; their mode is unknown). `SNAPSHOT` mode copies the source per deployment. Children inside appmux are not Databricks deployments, so appmux must snapshot them itself.

## Constraints

**Discovered**
- [Constitution](../../.specify/memory/constitution.md): children stay standard apps (no `app.yaml` or source changes); a route opens only after fetch → build env → start → health check; adding or updating never interrupts running apps.
- Stack direction (user, 2026-10-30, round 8): Python for the supervisor, edge, reconciler, pump and API, and a Next.js admin UI shipped as a static export; recorded in [ADR 0012](../decisions/0012-build-services-in-python-and-the-admin-ui-in-nextjs.md), with the HTTP stack in [ADR 0014](../decisions/0014-build-the-edge-on-the-environments-http-stack.md). ADRs are append-only.
- Databricks Apps container, measured on Free Edition on 2026-10-29: uid 1000, no sudo, no seccomp, `ptrace_scope` 0 (same-uid processes read each other's `/proc/<pid>/environ`, PID 1 included), `/databricks/runtime-secrets/runtime.cfg` readable by the same uid, no cgroup writes, `oom_score_adj` writes denied, only rlimits (`RLIMIT_AS` enforced), memory limit 8 GiB, 4 CPUs visible, `NPROC` unlimited, `/dev/shm` 64 MB, `/tmp` survives a redeploy (the app dir does not), Python 3.11 and Node 22.
- `/dev/net/tun` is absent, so TAP-based user-mode NAT (`slirp4netns` default, `pasta`) fails. User, mount, net and pid namespaces work unprivileged through `unshare`.
- Lakebase (Autoscaling, `databricks postgres`): a service principal connects through an OAuth Postgres role; the token is the password, lives 1 hour and is checked only at login; role management needs the project's CAN MANAGE; GRANTs apply per branch. Free Edition limits (3 apps, 24-hour auto-stop, one Lakebase project, trusted-domain egress, fair-usage shutdown) and the container measurements are recorded in [reference/databricks-free-edition.md](../reference/databricks-free-edition.md).
- Databricks Apps user authorization has a `postgres` scope, but AppKit v1 does not enable it and the docs do not say it logs in to Lakebase. Measured (spike 1, Free Edition): a user's token logs in to Lakebase **with or without** that scope, and only validity is checked, so a scope does not limit a token there. Scopes are per app, so every child granted OBO receives tokens carrying the same scopes.
- Platform request path and identities, with sources ([reference/databricks-apps-platform.md](../reference/databricks-apps-platform.md)): only the appmux app has an automatic service principal (children inside it have none, and a hand-made SP is a workspace-admin action); Unity Catalog grants come from the object's owner, a `MANAGE` holder or a metastore admin; the proxy reaches the app from loopback; the app must support H2C and exit within 15 seconds of `SIGTERM`; the docs say nothing about base paths, WebSocket, timeouts or size limits.
- Secrets (checked 2026-10-30): a Databricks App receives a secret by having it as a resource, injected into that App's environment through `valueFrom`; permission is granted per secret scope, not per key. The Secrets API call that returns a value (`get-secret`) is documented as callable only through the `DBUtils` interface. Spike 11 (Free Edition, 2026-10-30) found that an App's SP reads a value with `READ` on the scope, by REST and by the SDK, so appmux can read a child's scope with its SP.
- Bundle and environment facts (checked 2026-10-30): a `databricks.yml` declares an app's resources under `resources.apps.<key>.resources[]`, each with a `name`, an optional `description` and one type key (`secret`, `sql_warehouse`, `job`, `serving_endpoint`, `experiment`, `genie_space`, `database`, `postgres`, `uc_securable`, `app`); `app.yaml` refers to a resource by that `name` through `valueFrom`. The system-environment page lists no pre-installed Python packages; an App's own Environment tab shows what it has ([reference/databricks-apps-platform.md](../reference/databricks-apps-platform.md)).

**Supplied**
- Registered apps ≤ ~100 (soft); how many run at once is unknown. One team owns the children. Mostly FastAPI, plus Streamlit, Dash, Gradio and Node.
- Convenience versus safety, not extreme: do not remove child features to gain safety.
- OBO and SP are both allowed per child, default-deny. The platform admin decides whether OBO, or the shared SP, may be **passed down** to a child (a delegation); the child's own admin cannot turn either on, but can **ask for it inside appmux** with a reason, and the platform admin approves or denies (user, 2026-10-30). The platform admin sets limits; the app admin cannot change `source_path`, the slug, the name or the budget directly, but can ask for a change inside appmux. Egress rules are set per app by a platform admin and are read-only for the app admin (user, 2026-10-30, round 8). Anyone who can reach appmux may ask for a new app, and a platform admin approves or denies it (user, 2026-10-30).
- Routing in v1 is by path prefix only (user, 2026-10-30; on 2026-10-29 the user had chosen `prefix`, `prefix-rescue` and `root`). Other methods are deferred, but the code must keep routing behind a `RouteSelector` interface so adding one means adding a module ([design §7](v1-design.md#7-request-path-and-routing)).
- Permissions mirror Databricks Apps: the principals are the users and groups Databricks already has, granted by email or by group, and the levels are `CAN_USE` and `CAN_MANAGE`. appmux keeps no groups table of its own (user, 2026-10-30).
- Packages and environments install from wheel files in workspace folders, because the company package index is blocked from the workspace. This applies to the children and to appmux itself (user, 2026-10-30). Wheel folders are declared per child and the wheels are kept once in a central store (user asked central versus per child; 2026-10-30). The app environment's own packages are used first and a wheel may overwrite them: the company index cannot be reached, but what the environment already has can be used (user, 2026-10-30, round 5).
- Resources and secrets get a resources table like a real app's, recording which user attached each; for a resource such as Lakebase, appmux checks the attaching user's own OBO (user, 2026-10-30). Each app declares its **own** resources (they are not a subset of the platform's), and the attach check mirrors what a standalone deploy needs; a `databricks.yml`, when the source has one, is accepted and loaded into the visual config as an offer (user, 2026-10-30, round 5). A secret is attached as a resource, not typed into the UI (user, 2026-10-30, round 5).
- No `app_type`: the runtime and framework are detected from the files, as Databricks does (user, 2026-10-30).
- Deploying on appmux follows the standalone logic: appmux reads the child's own `app.yaml` for its `command`, `env` and the resource keys it needs, and sets the environment a standalone App gets (user, 2026-10-30; [design §5.4](v1-design.md#54-appyaml-requirements-and-start)).
- Keep the design and the registry simple (KISS): the registry holds decisions and history, not runtime state, in nine tables (user, 2026-10-30), each documented with its columns, example rows and DDL (user, 2026-10-30, round 5).
- App admins can roll back to any version, delete versions, and name or tag them; the platform admin sets the maximum number of versions kept, which is not hard-coded (user, 2026-10-30). Tags protect nothing; protection is a **lock**: the active release is locked by default, an app admin can lock others up to a maximum, and a release that is neither active nor locked can be deleted (user, 2026-10-30, round 5).
- Reading `source_path` uses the OBO token of whoever presses Update, not the child's or appmux's service principal (user, 2026-10-30).
- A child that does not accept the shared SP uses its own SP (user, 2026-10-30).
- Shared-SP is kept (user, 2026-10-29). It is a per-app config that the platform admin enables only after judging it necessary and safe for that app.
- Source is a workspace folder (the user chose option A). Git is a later addition.
- A few minutes of full outage when appmux restarts is acceptable.
- Free Edition is the development environment; probe app `appmux-probe` is still deployed there.
- v1 is the data plane, registry, launcher and admin UI, metrics dashboard, and basic RBAC with per-app access lists and app admins.
- An update runs the new release next to the old one and swaps the route only after the health check, so an update causes no downtime. It needs the app's budget twice during the update; admission control refuses the update when the budget cannot hold both (confirmed 2026-10-29).
- The audit log is in v1 (confirmed 2026-10-29).
- Standing design premises (user, 2026-10-29), checked on every design decision: (1) no permission path may need a Databricks workspace admin — where a service principal would need an admin's grant (for example `USE CATALOG` in Unity Catalog), use OBO (a personal access token would be the worst case, and is out of v1: 2026-10-29); (2) for every design ask "if the child is malware, can it do harm?" and state the trade-off; (3) many apps in one slot is the purpose of the repo; (4) every config states its level of effect (all children, one child, or per user through OBO); (5) where a risk cannot be removed by mechanism, it is gated by a per-app approval from the platform admin with a recorded reason, and the design states what the gate costs (review latency, reliance on one person's judgment, rubber-stamping), so gates stay few.

**Assumed (flagged, awaiting confirmation)**
1. If logging in to Lakebase with an OBO token fails, shared-SP mode is dropped and the SP writes everything.
2. `owner` is one user email, changed only by a platform admin directly; deleting an app is platform-admin only; granting OBO needs a platform admin's approval.
3. New apps default to pass-through egress. Metrics keep 7 days at 1-minute resolution. Child logs, run state and events are in memory only.
4. appmux reads `command` and `env` from the child's own `app.yaml` and resolves each `valueFrom` key from the app's resources table, so the child needs no change. Both `app.yaml` and `app.yml`, or an `env` entry with both or neither of `value` and `valueFrom`, refuse the Update; unknown keys only warn. A release whose keys are not all resources fails before any build, listing every missing key, and is activated after the admin attaches them. Children run on the parent's Python 3.11 and Node 22 and get no telemetry. The source's `databricks.yml`, if present, is read only to **offer** its `resources` in the Requirements panel; nothing is attached until the admin confirms, and an invalid file never refuses an Update ([design §5.4](v1-design.md#54-appyaml-requirements-and-start)).
5. Group grants match the Databricks groups that the SCIM current-user endpoint reports for the visitor, called with the visitor's own token and cached for 300 seconds; direct and indirect (nested) memberships both match, measured by spike 12 on 2026-10-30. A platform admin holds `CAN_MANAGE` on every app implicitly, with no row in `app_grants` (user, 2026-10-30, round 8): they can open it, read the source of its releases in a read-only viewer (each view is audited as `release.view_source`) and edit its configuration. The token is the admin's choice (user, 2026-10-30, round 8): a platform admin who is neither the owner nor named by a grant opens an OBO-delegated app in one of two modes, **without token** (the default) or **as a user** (the token passes; audited as `app.view_as_user`), so no `CAN_USE` self-grant is needed. The first platform admin comes from a deploy-time list that is honoured only while the `platform_admins` setting is unset; at least one `user` entry must always remain.
6. A child's secret is a `secret` resource that is a **reference** (`scope/key`): the attach check reads the secret as the attacher (a SQL `secret()` call, because the key listing needs a scope no App accepts), and the appmux SP reads the value when the child starts, from a scope whose manager gave the SP `READ` ([design §8.3](v1-design.md#83-secrets-where-the-value-comes-from)). Spike 11 confirmed that an App's SP can read values, so references ship and the encrypted store is not planned. A consequence now confirmed: with references, the appmux SP holds `READ` on every referenced scope, so a shared-SP child can read them (design §8.4, O1).
7. Opening an app and managing it are separate: `CAN_MANAGE` includes `CAN_USE`; `everyone` can be granted `CAN_USE` only.
8. A delegation is a flag on the app that a platform admin sets. The app admin asks in appmux with a reason and the platform admin approves or denies in an inbox. The same mechanism carries every other change that only a platform admin may make on one app: one table, `permission_requests`, with a `kind` and a `payload`; three kinds in v1, one per functional group (user, 2026-10-30, round 8): `register` (a new app), `delegation` (`obo`, `shared_sp` or both) and `settings` (any of `slug`, `display_name`, `source_path`, `memory_budget_mb`, together in one request); `register` is the one kind with no app yet: any visitor may ask, its slug waits in the payload (`app_slug` is null until approval) and one person may have at most 3 pending; a kind is an entry in code with its fields, and being a gate belongs to a field, so adding a field or a kind needs no migration; approving applies exactly what was asked, every field or none; `register`, `source_path` and each delegation flag are the gates and pass three gates (register an app, OBO, shared SP), so the gates stay three. A slug may be renamed by request or by a platform admin's edit; if the slug is taken when a platform admin presses Approve, the request is closed `denied` automatically (user, round 8). The owner and the egress rules are a platform admin's direct edit, not requests; the health check is the app admin's own setting, not a request. A request grants nothing (only the change on `apps` does); one pending request per app and kind; self-approval is allowed and recorded; there is no notification outside the UI; a `shared_sp` request is refused while the master switch is off; deleting an app and access requests are not requests in v1 ([design §9.4](v1-design.md#94-requests-to-a-platform-admin), [§8.1](v1-design.md#81-the-three-modes-and-delegation-requests)).
9. The release cap is a platform setting that defaults to 10, with no per-app override. A release is **protected** while it is active (locked by default), the target, in progress, or locked by hand; the platform setting `max_locked_releases` (default 3, at most the release cap minus 4) caps the manual locks per app. When an Update would exceed the cap, appmux deletes the oldest unprotected release; if none qualifies, the Update is refused. A release that stops being active and is not locked can be deleted at once. Tags are free labels, not unique, and protect nothing.
10. Resources, secrets and the own-SP keys belong to the app and take effect at its next start; they are not versioned by release.
11. If an OBO token cannot read workspace files (spike 15), the fallback is the earlier design: the folder owner grants the appmux SP read access to the registered folder.
12. `source_path` stays a platform decision, because it decides what code runs in the slot: set when a platform admin registers an app or approves a `register` request, and changed only by a platform admin or by approving a `settings` request that holds it.
13. Packages resolve **environment first**: a requirement the app environment satisfies is used as it is and nothing is fetched; otherwise a wheel (pinned with a hash) is installed into a per-release overlay that wins over the environment copy; otherwise the index (index modes) or the Update fails listing every unresolved requirement at once. Hashes are required only for pins the environment cannot satisfy. The environment and every overlay are read-only inside children ([design §5.3](v1-design.md#53-build-and-package-sources)).
14. **Licence:** Apache-2.0 (user: choose whatever fits, 2026-10-30), proposed because it carries a patent grant and suits a tool that runs other people's code. No `LICENSE` file is added before the design is approved. `slirp4netns` (believed GPL-2.0) is fetched at install with a checksum and never committed (spike 9); the release zip carries it with its source, as the owner accepted in [ADR 0015](../decisions/0015-bundle-slirp4netns-in-the-release-zip-with-its-source.md).
15. **Admin UI:** a Next.js static export built before deploy and served by the Python edge, polling a JSON API every few seconds under a strict CSP (`script-src 'self'` plus per-page hashes of the inline scripts, spike 19). This replaces the earlier "no front-end build step" (spike 19).
16. **Added in round 8, awaiting confirmation:** the default of the two admin view modes is "without token", and the mode is kept in an edge cookie that is removed before forwarding (assumption 5); the egress editor refuses an `allow` that overlaps `@container_ip`, `@appmux_port` or `169.254.0.0/16`; an automatic denial records the admin who pressed Approve as `closed_by`; renaming an app restarts a running one through the normal swap and the old URL answers `404`; `ON UPDATE CASCADE` with deferrable composite keys works under the platform admin's role (spike 9).

## Chosen approach — sandboxed supervisor

One Databricks App runs the appmux supervisor: an edge that routes requests, a reconciler that is the only component allowed to open a route, a sandbox launcher that puts each child in its own user, mount, net and pid namespaces, a Lakebase registry, an admin UI and metrics. The full behaviour is described once, in [v1-design.md](v1-design.md); this section lists the decisions that answer the constraints above and where each is specified.

- **Isolation:** unprivileged namespaces, a veth pair with an `AF_PACKET` frame pump feeding `slirp4netns --netns-type=tapfd`, egress rules enforced in the pump, a fail-closed `self_check()` at startup ([design §6](v1-design.md#6-isolation-and-network)).
- **Releases:** a snapshot is taken only when an admin presses Update; a release is snapshot plus config; an update runs next to the old release and swaps the route after the health check; rollback activates any live release; app admins name, tag, lock and delete releases within a cap the platform admin sets ([design §5](v1-design.md#5-child-lifecycle)).
- **Deploy contract:** the child's own `app.yaml` is parsed at Update; the resource keys a release needs are checked before any build and all missing ones are listed; the environment a standalone App gets is set; the differences from a standalone App are listed ([design §5.4](v1-design.md#54-appyaml-requirements-and-start)).
- **Routing:** path prefix only in v1, behind a `RouteSelector` interface with a module boundary per concern (identity, routing, authorization, rewriting, upstream); no response-body rewriting ([design §7](v1-design.md#7-request-path-and-routing), [§3.4](v1-design.md#34-module-boundaries)).
- **Packages:** the app environment first, then wheels in a per-release overlay that overwrite it, then the index; modes `index`, `wheelhouse` or `wheelhouse+index`; wheel folders are declared per child (its own `wheels/`, extra folders, optional platform defaults), a hash-pinned wheel lock names the wheels the environment cannot provide, and they are kept once in a central content-addressed store with a wheel list per release ([design §5.3](v1-design.md#53-build-and-package-sources)).
- **Credentials, resources and secrets:** OBO and shared SP delegated per app by a platform admin, who answers requests from the app admin inside appmux (the shared SP with its exposure listed; the same request table also carries a new app and changes to an app's name, slug, source folder and budget), and own SP; a resources table where each app declares its own resources (by hand or from the source's `databricks.yml`) with an attach check made with the attacher's own token; a child's secret is a reference to a scope key (an encrypted store inside the registry only as a fallback, spike 11); PAT is not in v1 ([design §8](v1-design.md#8-identities-secrets-and-resources)).
- **Registry:** nine Lakebase tables that hold decisions and history, not runtime state, with platform data written through the platform admin's OBO identity and app-admin data and results through the SP, plus an audit log ([design §4](v1-design.md#4-registry), [data model](v1-data-model.md)).
- **Roles and config levels:** `CAN_USE` / `CAN_MANAGE` for Databricks users and groups (groups read through the visitor's own token); one table-driven `authorize()`; every config states its level of effect ([design §9](v1-design.md#9-roles-permissions-and-config-levels)).
- **Stack and UI:** Python services; a Next.js admin UI as a static export served by the edge, with a JSON API and a strict CSP ([design §10.1](v1-design.md#101-screens)).
- **Testing:** 10 well-behaved fixtures, about 10 hostile fixtures, 2 routing fixtures, 4 offline-install fixtures, 2 `app.yaml` fixtures and a `databricks.yml` fixture, logic tested locally, sandbox integration only on the Databricks container ([design §14](v1-design.md#14-testing)).

## Alternatives considered

| Option | Why it lost |
|---|---|
| Flat supervisor, no namespaces | Measured: environ of siblings and PID 1 readable, 77 of 89 localhost ports reachable, `runtime.cfg` readable. Contradicts "assume a child is malware". |
| Shard children across several slots | Spends the scarce resource and gives no isolation inside a slot. Kept as a later escape hatch. |
| TAP-based NAT (`slirp4netns` default, `pasta`) | Disproven: `/dev/net/tun` is absent. |
| `--disable-host-loopback` alone | Blocks host loopback (0/90 vs 78/90 ports) but not the container IP, appmux's port or `169.254.169.254`. |
| Blanket private-range deny | Also blocked the workspace host, which resolves to a private address. |
| Host-based routing | One hostname per App. |
| Root `/` routing by cookie as the only mode | One app per browser, tabs conflict. Deferred behind the selector interface with `prefix-rescue`, not built in v1. |
| Port-based or query-parameter selection | One port reaches the app; a query parameter is lost at the first link or redirect. |
| Rewrite response bodies (nginx `sub_filter`) | Misses URLs built in JS or JSON, breaks streaming, buffers every response in the shared edge. |
| SP-only writes to Lakebase | A shared-SP child could overwrite platform data. |
| OBO-only writes to Lakebase | App admins would each need a Postgres role, and the OBO login is unproven. |
| Stop-then-start updates | The updated app is down during fetch and build, and stays down if the new release is bad. |
| Typed secret values in an encrypted store inside appmux as the only secret source | appmux then holds a master key and every child's secrets and needs a write-only screen and a rotation story. Not planned: spike 11 showed an App can read a scope. |
| Attach each child secret as a resource of the appmux App | Every new secret would edit and restart the appmux App, interrupting all children, and app admins cannot do it. |
| Install packages only from the package index | The company index is blocked from the workspace. |
| A virtualenv per release | Measured locally: a `--system-site-packages` venv created inside a venv does not see the parent's packages, and a venv per release costs time and space. An overlay holding only the wheels that must differ, ahead of the environment on `PYTHONPATH`, wins over the environment copy. |
| Tags that protect a release | Protection by tag was implicit and unlimited; a lock is explicit and capped (user, 2026-10-30). |
| Ignore `databricks.yml`, or apply it as the source of truth | Ignoring it loses what the author already wrote; applying it would attach resources with no permission check of a person. It is read as an offer and the admin confirms each resource. |
| appmux's own `groups` and `group_members` tables | Duplicates Databricks' directory and needs a platform admin to maintain it; Databricks grants by email or group already. |
| Declare an `app_type` at registration | The runtime and framework can be detected from the files, as Databricks does; a declaration can disagree with the files and does no work that detection cannot. |
| One central wheelhouse folder that every app must use | Every app waits on whoever can write it, and every file in it is offered to every app. |
| One private wheelhouse per child with no sharing | A heavy wheel such as `pandas` would be stored and fetched once per app. |
| Read `source_path` with the appmux or the child's service principal | The folder owner must grant the SP per app, and appmux reads with rights the presser may not have (a confused deputy). The presser's own token is the right bound. |
| The app admin turns OBO or the shared SP on for their own app | How far a credential reaches is the platform's decision, not the child's admin's. |
| A fixed number of retained releases | The cap is a platform setting, and the app admin keeps the versions that matter by locking and deleting. |
| Ask a platform admin for a delegation or a field change outside appmux | A side channel leaves no record and gives the reviewer no context; a request with a reason, answered in appmux and logged, costs little more. |
| One request kind per field (the earlier draft had eight) | A form per field, and a new name with a new budget needed two requests. Grouped by function (a new app, a credential, settings), one request carries several fields, and being a gate belongs to the field. |
| A slug fixed for the life of an app | Renaming is a real need (user, round 8). `ON UPDATE CASCADE`, a restart through the normal swap and an automatic denial for a taken slug make it one request. |
| Egress rules as a request, or edited by the app admin | Where a child's code may connect is the platform's judgment from the start (user, round 8): a platform admin sets it per app and the app admin sees it. |
| No platform-admin access to apps they do not own | Supporting 100 apps would need a grant per app or a hand-edited database. Implicit `CAN_MANAGE` is audited, and the admin's token reaches an app only when they choose **Open as a user**. |
| One table per concern (the earlier draft had 20), or one `apps` table with column-level `GRANT` | More tables meant more writers, joins and migrations, and some held only runtime state. Column `GRANT` is unverified on Lakebase and harder to review than two tables with one writer class each. Nine tables keep one writer class each. |
| Persist run state and events in the registry | The reconciler rebuilds run state from decisions at start; persisting it adds writers and tables with no decision to audit. |
| Make the admin re-declare env and resources in appmux, ignoring `app.yaml` | It duplicates what the child already says and drifts from it; the requirement was the same logic as a standalone deployment. |
| Ask Databricks to raise the 100-app cap | The cheapest premise check. Raised during the session; the user did not pursue it. |

## Out of scope / anti-goals

- Replacing Databricks Apps, or requiring any change in a child's `app.yaml` or source.
- Not in v1: routing by anything but the path prefix (`prefix-rescue`, `root`, header), requests for deleting an app, for a new owner or an egress rule (a platform admin's direct edit), for a platform setting, or decided by an app admin (access requests), time-limited approvals, notifications outside the UI, evaluating `${…}` and variables in `databricks.yml`, other Python versions per app, persisted runtime events, a pooled service principal, a master-key rotation screen (fallback store only), an npm offline source, personal access tokens as a child credential (user, 2026-10-29), sleep and start-on-request, sharding, hostname egress rules, IPv6, response-body rewriting, Git source, automatic rollback, an audit-log UI, alerts, per-user usage analytics, editing source in the UI, release diff, preview of a release before promotion, canary traffic, blue/green of appmux itself.
- No promise to stop data leaving through allowed destinations or DNS; egress defaults to pass-through.
- No hard CPU or process limits (no cgroups); no guarantee beyond what `self_check()` measures.

## Success criteria

1. **No disruption.** With steady load on app A through the proxy, these operations cause no more failed requests than a no-op control run of the same length: register app B, update B, update A with a good release, update A with a release that fails health (A keeps serving; the release is `failed`), a heavy build in parallel, an egress rule edit. p95 before and during is reported.
2. **Fail-closed isolation.** `self_check()` passes on a healthy sandbox. For each deliberate weakening (skip the `/proc` overmount, skip the capability drop, disable the pump filter) it fails, appmux opens no route and shows the status page. The hostile fixtures read no secret or env of another app.
3. **Capacity with 10 simulated apps.** Report RSS per app (idle and loaded), per-sandbox overhead, start time, CPU and total against the slot limit, and an explicitly labelled linear estimate for 100 apps. One hard condition: with the budget set for 10 apps, the 11th is refused with a clear reason.
4. **No hand-edited database.** A scripted walkthrough through the UI or API (register an app directly, request and approve a new app, request and approve an OBO delegation and a settings change (name and memory budget), rename an app by request (and a rename to a taken slug, which closes automatically), set an egress rule as a platform admin, open another team's app and read its snapshot source as a platform admin, share an app with a user and with a Databricks group, make someone an app admin, attach a resource (including a secret) and accept an offer from `databricks.yml`, update, tag, label, lock, unlock and delete a release, activate an older release, restart, stop) runs with no SQL typed, and the final DB state matches the expectation.

## Open questions

Spikes that gate the plan, in order. Each can change the design. **All ran on 2026-10-30 (spike 3 was dropped); the results are in the [spikes log](../../specs/001-appmux-v1/spikes/README.md) and the decisions they fixed are in the [plan](../../specs/001-appmux-v1/plan.md#decisions-from-the-spikes).**

1. **Lakebase login with an OBO token carrying the `postgres` scope.** Blocks the platform-admin write path. Needs a Lakebase project (the workspace has none yet) and a role for the tester. Fallback is assumption 1.
2. **Filesystem exposure beyond `/proc`, `/tmp` and runtime-secrets** (app dir, home, `/dev/shm`, other mounts). Blocks the mount allow-list design. Unblocked by a probe on the Databricks container.
3. **Do these measurements hold on a paid workspace?** Unblocked by re-running the probe there; whether the user has access to one is unknown.
4. **Can the appmux SP write snapshots to its own workspace folder ?** If not, the durable content store (snapshots and wheels) needs another home (a UC Volume is a candidate, unchecked).
5. **Base-path support per framework** (uvicorn `--root-path`, Streamlit, Dash, Gradio) and the environment variable each reads, which decides whether appmux can set the base path without changing the child. With path-prefix routing the only v1 mode, this decides which apps v1 can host at all; an app that hard-codes absolute links gets a 404 on its assets.
6. **Egress mechanics:** live rule reload, port rules, fragment handling, whether neighbouring containers on the same subnet are reachable.
7. **Edge and pump throughput under load, fork-bomb and CPU hogging, source builds that need a compiler.** Measured by criteria 1 to 3 and the hostile fixtures; may force a faster pump or a wheels-only rule.
8. **Behaviour of the Databricks proxy** that the docs leave unstated ([reference](../reference/databricks-apps-platform.md)): are arbitrary sub-paths forwarded, WebSocket and SSE, idle and total timeouts, body and header size limits, `Set-Cookie` handling, whether client-supplied `X-Forwarded-*` headers are overwritten, HTTP/1.1 versus H2C toward the app; and whether the proxy accepts the CLI's OAuth token as a bearer, which decides how load can be generated. Decides routing and how far identity headers can be trusted.
9. **Cascade privileges on Lakebase** (a platform admin's `DELETE` on `apps` cascading into tables that role cannot write; the same for an `UPDATE` of `apps.slug` with `ON UPDATE CASCADE`, and whether the deferrable composite keys of `app_config` let a rename through), `SET LOCAL ROLE`, and the `slirp4netns` licence (believed GPL-2.0), which decides whether the binary is fetched at install with a checksum instead of committed.
10. **How a child refreshes a shared-SP token.** The token is short-lived (1 hour) and the child never gets the client secret, so a static environment variable expires. Candidates: appmux re-injects through a local endpoint the SDK can call, or a file the child reads. Unverified; decides whether shared-SP works with unmodified SDK code (constitution I). Includes whether the token request accepts a narrower OAuth `scope` than `all-apis` (design §8.4, measure O3).
11. **Secrets API from an App.** Can the appmux SP, or a token minted for it, read a secret value (`get-secret` is documented as `DBUtils`-only) from inside an App, and does the attach-time key listing work with an OBO token? A "yes" ships secret references; a "no" ships the encrypted store and drops the references. A "yes" also means a shared-SP child could read every scope the SP has `READ` on (design §8.4, O1). Needs a secret scope in the workspace, created with the user's go-ahead.
12. **Nested groups in SCIM `Me`.** The current-user endpoint called with the visitor's token returns the person's groups; does it include groups reached through nesting, or direct memberships only? Decides whether a group grant covers nested groups.
13. **Parent-app wheel bootstrap.** Does the platform honour `--no-index` and `--find-links` lines in an App's `requirements.txt`? If not, appmux needs the stdlib bootstrap that installs its own wheels at start ([design §13.1](v1-design.md#131-what-the-operator-sets-up)).
14. **Offline source for Node children** (an npm cache or tarballs), and wheel coverage: whether every package the target apps need has a `manylinux` wheel for Python 3.11, and which of them the app environment already provides.
15. **Workspace file read with the presser's OBO token.** Which scope lets the appmux App list and export a workspace folder as the user (`workspace.workspace` with a `:read` form is the candidate), and whether the workspace's scope allowlist includes it. A "no" brings back assumption 11.
16. **Per-type attach checks.** For each of the 14 resource types, the read-only call that shows the attacher's access, and the OAuth scope it needs. Types with no usable call stay `unverified` and cannot be used with `shared_sp`.
17. **`app.yaml` on the real platform.** Whether `$DATABRICKS_APP_PORT` is substituted inside a `command` argument and with what syntax, what Databricks does for a `valueFrom` key with no resource, and the full list of variables a real App receives, compared with the documented list. Measured on `appmux-probe` ([design §5.4](v1-design.md#54-appyaml-requirements-and-start)).
18. **Package overlay on the real container.** `pip install --no-index --no-deps --require-hashes --target` into an overlay, `PYTHONPATH` ahead of the environment, entry-point scripts run from the overlay's `bin`, and whether the read-only remount of the environment and the overlays holds inside the sandbox. Also read the Environment tab of `appmux-probe` to see what the environment provides ([design §5.3](v1-design.md#53-build-and-package-sources)).
19. **Next.js admin UI on the platform.** Whether a static export works under a strict CSP (no inline script) and a base path behind appmux's own prefix, and whether the platform builds a `package.json` in a Python App; if not, the export is built before deploy and ships with the source ([design §10.1](v1-design.md#101-screens)).
