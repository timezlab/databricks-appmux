## TD-001: Harness updates are manual
- **Where:** `.agents/` (skills, agents, rules, hooks copied from `timezlab/vibe`)
- **Symptom:** upstream changes do not reach this repo, and after a manual re-copy a path rewrite can be missed, leaving a skill that runs `hooks/learned/...` — a path that does not exist here ([reference](reference/agent-harness.md#updating-from-upstream)).
- **Why deferred:** vibe's `vibe sync` is planned, not implemented; the harness only needs an occasional refresh.
- **Trigger to fix:** vibe ships `vibe sync`, or the second manual update is needed.
- **Created:** 2026-10-29

## TD-002: An OBO child's token reaches the registry
- **Where:** [ADR 0004](decisions/0004-keep-decisions-in-a-nine-table-lakebase-registry-with-split-writers.md), [design 4.2](product/v1-design.md#42-who-writes-what), `registry` module
- **Symptom:** Lakebase checks that a token is valid but not its OAuth scopes (spike 1), so an OBO-delegated child holds a token that logs in to the registry as the visitor. For a platform admin that includes the platform-data writes, and a connection the child opened keeps working after the token expires.
- **Why deferred:** the owner accepted the residual on 2026-10-30 (spec question 5, option a); the alternative gives up the separation between a person and the appmux SP. A platform admin's default view mode stays *without token* (A1) so the token is not sent unless asked for.
- **Trigger to fix:** Lakebase starts enforcing token scopes, or a way to mint a registry-blind OBO token appears.
- **Created:** 2026-10-30

## TD-003: CPU and memory limits are best-effort
- **Where:** `sandbox` module, [design 5.7](product/v1-design.md#57-memory-and-admission-control), [spike 7](../specs/001-appmux-v1/spikes/README.md)
- **Symptom:** the container denies cgroup writes, so there is no hard cap. A CPU hog stalls the others about 50 ms; pinning children to one CPU at `nice 19` with `sched_setaffinity` refused by seccomp brought the victim's p95 to 1.35 ms. Memory has an RSS watchdog and `RLIMIT_AS`, and a fast allocator can still push the container into an out-of-memory kill.
- **Why deferred:** no mechanism a non-root process can use gives a hard cap on the platform. Fairness among children that share the pinned CPU, a memory hog, and pinning without `nice` were not measured.
- **Trigger to fix:** the platform allows cgroup delegation, or SC-003 shows a noisy child hurting a neighbour.
- **Created:** 2026-10-30

## TD-004: A child's run-directory size cap is unproven
- **Where:** `sandbox` module, [design 6.1](product/v1-design.md#61-sandbox)
- **Symptom:** a size-limited tmpfs returned ENOSPC at its cap, but the host-backed run directory is unbounded. The two planned caps (a pre-bound socket descriptor with a size-limited tmpfs, and a size watchdog) have not been run.
- **Why deferred:** found in spike 7 late; the plan picks the tmpfs and the watchdog as a fallback and the first `self_check` canary proves whichever is used.
- **Trigger to fix:** the canary cannot prove the cap, or tmpfs memory accounting counts against the child's budget.
- **Created:** 2026-10-30

## TD-007: `GET /requests` returns the whole history
- **Where:** [admin API contract](../specs/001-appmux-v1/contracts/admin-api.md) `GET /requests`, [data model §8](product/v1-data-model.md) (requests are kept forever)
- **Symptom:** the list is neither filtered nor paged, so the response and the UI grow with every request ever made; the three views of T141 (own, an app's, the inbox) are the client's own union of what the actor may see.
- **Why deferred:** the design paginates only audit and metrics; a few hundred requests a year does not hurt, and a filter or cursor is a contract change that needs a use case.
- **Trigger to fix:** a response above about 1 MB, or the inbox taking more than a second to render.
- **Created:** 2026-10-30

## TD-008: No step of the operator flow applies the baseline schema
- **Where:** [design 13.1](product/v1-design.md#131-what-the-operator-sets-up), `src/appmux/registry/migrations.py` (the loader, Wave 2), [tasks.md](../specs/001-appmux-v1/tasks.md)
- **Symptom:** the loader applies `migrations/*.sql` in one transaction, but no task adds a command that calls it and design 13.1 has no "load the schema" step between creating the Lakebase roles (item 2) and the first start (item 7). The appmux SP cannot create the tables itself (it is not the table owner and holds no DDL grant), so the operator must run the loader with their own credentials.
- **Why deferred:** found when the loader was reviewed on 2026-10-30; the entry point needs a decision on who runs it (the operator's laptop against Lakebase, or a one-off command inside the App) and how that run logs in.
- **Trigger to fix:** before the first deploy that needs a real database; add the command, a design 13.1 step and a task, and cover the refusals (`apps` already exists, a role missing) in the quickstart.
- **Note (2026-11-03):** until that command exists, a migration after the baseline is applied by hand to a loaded registry, for example `psql -v ON_ERROR_STOP=1 -f migrations/0003_service_principal_grants.sql`. Such a file is written to be safe there: one statement, so it applies whole or not at all without a `BEGIN`, and re-runnable (`DROP CONSTRAINT IF EXISTS` before each `ADD`). It holds no `BEGIN`/`COMMIT`, because the loader runs every file inside its own transaction.
- **Created:** 2026-10-30

## TD-020: A shared-SP delegation reaches a running child only after a restart, and a service principal can be admitted only by `everyone`
- **Where:** `src/appmux/admin/delegation.py` (grant), `src/appmux/admin/apps.py` (`restart_to_apply`, a placeholder that is always `false`), `src/appmux/admin/schemas.py` (`GrantRequest`: a `user` grant takes a lower-case email), the edge's identity handling
- **Symptom:** (1) On the Free Edition dev App (2026-11-03) `PUT /apps/agent/delegation/shared_sp` answered 200 and the app read `shared_sp_delegated: true`, but the running child kept reporting "no Databricks credentials" (and did not restart) until `POST /apps/agent/restart`. - **Trigger to fix:** the first user who delegates the shared SP to a running child, or who wants a sibling App to call a child without admitting everyone.
- **Created:** 2026-11-03

## TD-021: The app page's egress editor writes outside the app page's write controller
- **Where:** `web/src/components/app/security/app-egress-section.tsx`, `web/src/components/platform/egress-editor.tsx`, `web/src/components/platform/use-write-action.ts`, `web/src/components/platform/action-result.tsx`
- **Symptom:** For a platform admin, the app's Security tab reuses the Platform page's `EgressEditor` inside a stand-in `PlatformProvider` (`refresh` is the app page's `reloadAll`, `announce` a live region of the section). Its Save therefore does not go through the app page's `actions.run` (`web/src/lib/app/writes.ts`): it is not refused while another write of the page runs (the server's `version` check still refuses a stale one with `409 changed_by_others`); its success sentence appears in the section, not in the notice under the header; and a `409 changed_by_others` shows the error with a Reload button instead of reading the app again by itself. Found by the T205 review (W13).
- **Why deferred:** `EgressEditor` and `ActionResult` take their write state and their reload from `useWriteAction` and `usePlatformContext`. Writing through `actions.run` needs `useWriteAction` to take its runner and its effects from the caller (or a second copy of its state machine on the app side), which is a change to every platform write, not to this section alone.
- **Trigger to fix:** the next change to `use-write-action.ts` or to the app page's write controller, or a report of an egress save racing another write on the app page.
- **Created:** 2026-11-03
