## TD-003: CPU and memory limits are best-effort
- **Where:** `sandbox` module, [design 5.7](product/v1-design.md#57-memory-and-admission-control), [spike 7](../specs/001-appmux-v1/spikes/README.md)
- **Symptom:** the container denies cgroup writes, so there is no hard cap. A CPU hog stalls the others about 50 ms; pinning children to one CPU at `nice 19` with `sched_setaffinity` refused by seccomp brought the victim's p95 to 1.35 ms. Memory has an RSS watchdog and `RLIMIT_AS`, and a fast allocator can still push the container into an out-of-memory kill.
- **Why deferred:** no mechanism a non-root process can use gives a hard cap on the platform. Fairness among children that share the pinned CPU and pinning without `nice` were not measured.
- **Measured 2026-11-05 (container, Free Edition; `tests/integration/test_failure_table.py` row 19, the memory hog):** with a 256 MB budget, a single-process hog was stopped by `MemoryError` from `RLIMIT_AS` (limit 512 MB) while holding 224 MB (288 MB in the first run), and the neighbour answered 200 throughout. A hog spread over four processes (600 MB in total, each far below the address-space limit) was stopped by the RSS watchdog at 491 MB against its limit of 384 MB ([TD-029](#td-029-the-rss-watchdog-is-written-and-tested-but-the-service-never-starts-it)). Neither run came near the container's 8 GiB. Not measured: a fast allocator that reaches the container's limit between two one-second readings, which is the gap that stays.
- **Also measured 2026-11-05 (`test_run_dir_cap.py`):** the pages a child writes into its run directory (a `tmpfs`) raise the container's memory in use and do not show in the child's own resident figure, so the watchdog cannot see them; the numbers are in [TD-004](#td-004-a-childs-run-directory-size-cap-is-unproven).
- **Also measured 2026-11-05 (`test_zero_downtime.py`, container, Free Edition):** with an app under 500 requests a second, three Updates building at once (`wheels_only`) raised the worst 5 s slice p95 from 16 ms to 1.88 s (median 970 ms, against 3.7 ms in the control) and the edge used 86 % of a core for those 12 s; no request failed. A second invocation measured 2.14 s for the same step. Why the builds cost the edge that much is not established, and no limit on parallel builds or on a build's CPU share is decided. Numbers: [spike log](../specs/001-appmux-v1/spikes/README.md#sc-001-no-disruption-under-operations-t108).
- **Trigger to fix:** the platform allows cgroup delegation, or SC-003 shows a noisy child hurting a neighbour.
- **Created:** 2026-10-30

## TD-004: A child's run-directory size cap is unproven
- **Where:** `sandbox` module, [design 6.1](product/v1-design.md#61-sandbox)
- **Symptom:** a size-limited tmpfs returned ENOSPC at its cap, but the host-backed run directory is unbounded. The two planned caps (a pre-bound socket descriptor with a size-limited tmpfs, and a size watchdog) have not been run.
- **Why deferred:** found in spike 7 late; the plan picks the tmpfs and the watchdog as a fallback and the first `self_check` canary proves whichever is used.
- **Measured 2026-11-05 (dev App, Free Edition, through its proxy; `tests/integration/test_run_dir_cap.py`, T060):** the run directory is a 64 MiB `tmpfs` inside the sandbox and it holds. `disk_filler` wrote 67 108 864 bytes (exactly 64 MiB) in 0.018 s and was refused with `ENOSPC`; `statvfs` of `/run/appmux` read 64 MiB; the child went on answering `200`. Spike 7's host-backed directory took 1 GiB in 1.5 s. The pages are memory, and they are counted in the container and not in the child: with 64 MiB written, the `_platform` row's `mem_used_mb` rose from 1 021 to 1 089 MiB (+68) while the child's own `rss_mb_max` went from 72 to 73 MiB. So neither the RSS watchdog nor `RLIMIT_AS` sees the run directory's pages. One run; the figures are one-minute peaks and the container's carries whatever else ran in it. Not run: `watch_run_dir` stopping a shared-service-principal child that overfills its host-backed directory (that directory has carried the child's token file in a container, T147), and the four other `tmpfs` mounts of a sandbox (design 6.1 gives `/tmp` 64 MB, `/var/tmp` 16 MB, `/dev/shm` 64 MB and `/home/app` 64 MB; they are the same kind of mount, so the same result is expected, which is an inference).
- **Still open:** the size cap is proven, but a sandbox can hold up to 64 MiB in its run directory, and by the inference above up to 208 MB more in the other mounts, outside the budget that admission control counts and the watchdog enforces. `OVERHEAD_PER_CHILD_MB` (64, [TD-032](#td-032-admission-assumes-13-mb-of-sandbox-overhead-and-the-measured-figure-is-61-mb)) is the measured cost of an empty sandbox, not of full mounts. Closing it means either counting the mounts' ceilings in the per-child overhead or lowering their sizes; that changes how many apps fit, so it waits for the owner.
- **Not measured, found in the T205 review (2026-11-05):** the cap is on bytes. The `tmpfs` mount data is `size=64m,mode=...` with no `nr_inodes`, so the number of files is capped only by the kernel default (half the RAM pages, per the kernel's tmpfs documentation), and `test_run_dir_cap.py` never creates a file beyond the one it fills. By kernel behaviour, from memory and not run here, each inode and dentry is kernel memory charged to the container's cgroup and counted in neither the `size=` cap nor the child's resident figure, so a child making millions of empty files could cost the container memory. A cap (`nr_inodes=` on the mount step in `sandbox/rootfs.py`) needs a number that does not break an app that writes many small files, and a container run to prove it, so the number is the owner's call. An unprivileged mount namespace could not be created on the dev machine, so it was not measured locally either.
- **Trigger to fix:** the first trigger (the canary cannot prove the cap) did not happen: the cap is proven. The second (tmpfs memory accounting) is the open item above: it has not counted against the child's budget, it counts against the container's.
- **Created:** 2026-10-30

## TD-022: A hidden value split by the partial-line flush reaches the output ring in part

  4. the same through the children: `test_an_own_sp_child_reads_a_foreign_secret_exactly_while_its_service_principal_holds_read` and its shared-SP twin pass (refused, granted and read, revoked and refused for 60 s without a break).
  So the `READ` grant alone decides whether a value is read; the listing shows names only. The containment tests accept `with token: list_scopes` by name (`PLATFORM_VISIBILITY`) and still require every secret read to be refused, so a read that succeeds without a grant fails them.
- **What stays true:** a scope's name is visible to every child; keep names free of anything that should not be known. The shared-SP fix O3 of 8.4 (a narrower OAuth scope on the lent token) would not remove it for an own SP, whose token appmux does not mint.
- **Trigger to revisit:** a measurement where a principal without `READ` reads a value, or a platform change that lists only the scopes a principal can read (then drop `PLATFORM_VISIBILITY` and the test fails if it was still needed).
- **Created:** 2026-11-04

## TD-029: The RSS watchdog is written and tested but the service never starts it
- **Where:** `src/appmux/sandbox/watchdog.py` (`watch`, `find_offenders`), `src/appmux/assembly.py` (nothing imported them until the fix below), [design 5.7](product/v1-design.md#57-memory-and-admission-control), [TD-003](#td-003-cpu-and-memory-limits-are-best-effort)
- **Symptom:** the design and TD-003 say a best-effort watchdog stops the one app whose process tree holds more than its budget with headroom. `watch` is called by no module in `src/`; only `RLIMIT_AS` (set per process in the launcher) limits a child. A child that spreads its memory over several processes, each under its own address-space limit, is not stopped by anything but the container's out-of-memory kill. T161 was ticked for the module, not for its wiring.
- **Why deferred:** found on 2026-11-04 by T180; `RLIMIT_AS` covers a single-process hog (`tests/integration/test_failure_table.py` row 19), and the wiring needs the reconciler's list of running children with their root pids, which T192 also needs for the metrics probes.
- **Measured 2026-11-05 (container, Free Edition):** `test_failure_table.py` row 19 passed: a child allocating without end held 288 MB under a 512 MB address-space limit (a 256 MB budget) and was stopped by `MemoryError`. That is the single-process case `RLIMIT_AS` covers; the several-process case is still unmeasured.
- **Done 2026-11-05:** the owner said to fix it. `Service.start_children` now starts `watch` once the reconciler is running (`Service._start_memory_watch`), over the sandboxes the reconciler reports (`SandboxRunningChild` with a known sandbox pid), once a second, reading `/proc` under the metrics root; `Service.stop` cancels it before the children are stopped. The limit is `budget × 1.25 + 64 MB`: the sandbox's own processes (pump, `slirp4netns`, supervisor, about 61 MB, TD-032) sit in the same tree, so without the allowance a 64 MB app (limit 80 MB) would be stopped while healthy. An offender is stopped with `SandboxRunningChild.stop_over_memory` (2 s grace, shorter than the run directory's 5 s because a child that is still allocating is an out-of-memory kill away from taking every app down); the child's exit carries "uses N MB, over its limit of M MB (budget B MB, plus 64 MB for the sandbox itself)", which the reconciler writes into that app's log and its crash report, and the app is restarted with backoff like any crash. Tests that failed before the wiring: `tests/unit/test_rss_watchdog.py` (allowance), `tests/unit/test_reconciler_sandbox_adapter.py` (the stop and its reason), `tests/contract/test_service_assembly.py` (the service starts the loop, stops only the offender, and not a 64 MB app inside its budget). The container hostile fixture `memory_hog_workers` and the test for it in `test_failure_table.py` were added with the fix; the single-process `memory_hog` gained a 5 s start delay, because the watchdog would otherwise stop it before its health check passes.
- **Measured after the fix, 2026-11-05 (container, Free Edition):** `tests/integration/test_failure_table.py` ran whole in one run on the dev App: `3 passed in 31.85s`. The `memory_hog_workers` child (4 workers × 150 MB, 600 MB in total, a 256 MB budget) was stopped by the watchdog: the App's log carries `stopping …: uses 491 MB, over its limit of 384 MB (budget 256 MB, plus 64 MB for the sandbox itself)`, the reconciler logged the death with that reason, closed the route and restarted the child after 1 s (the fixture allocates again on every start, and it was stopped again at 392 MB). The neighbour answered 200 throughout, and the reason read back from `GET /apps/{slug}/logs`. The single-process `memory_hog` (with its start delay) was still stopped by `MemoryError` at 224 MB held, below the watchdog's limit, so `RLIMIT_AS` stopped it, as before. Not measured: the cost of the per-second `/proc` scan with many children, and the run is one container on one workspace.
- **Trigger to fix:** met and done; the entry stays so the links to it keep working. What it does not cover: a fast allocator that reaches the container's limit between two readings (TD-003), and a tree whose memory is shared pages counted once per process (that over-counts, which the 25 % headroom absorbs).
- **Created:** 2026-11-04

## TD-030: A child whose `slirp4netns` dies keeps running with no way out
- **Where:** `src/appmux/sandbox/launcher.py` (`_wait_for_end` waits for the sandbox process, the wall clock and stop requests only), [design 11](product/v1-design.md#11-failure-behaviour) ("Child's pump or slirp dies")
- **Symptom:** the design treats a dead pump or `slirp4netns` as a crash of that child (no egress, then restart with backoff). The supervisor does not watch either helper, so the child keeps running, reports healthy, and fails every outbound call until someone restarts it. Read from the code on 2026-11-04; `tests/integration/test_failure_table.py` (row 20) kills the helper on a container and asserts the design, so it records the measured result.

- **Confirmed 2026-11-05 (container, Free Edition):** row 20 killed `slirp4netns` and, 90 s later, the child was still `running` in the same sandbox with no network helper; the supervisor had noticed nothing. The test failed and was left failing until the fix.

## TD-032: Admission assumes 13 MB of sandbox overhead and the measured figure is 61 MB
- **Where:** `src/appmux/reconciler/admission.py` (`OVERHEAD_PER_CHILD_MB`, whose comment says the capacity run replaces it), [design 5.7](product/v1-design.md#57-memory-and-admission-control)
- **Symptom:** `test_capacity.py` on a container (2026-11-05) measured 60.7–61.1 MB per sandbox (the sandbox's process tree minus the app's own RSS), the same for all four fixture kinds. Admission adds 13 MB per running app to its budget. While apps stay under their budgets the ledger is far above real use (ten apps: 1 385 MB of sandbox RSS against 6 992 MB committed), so nothing broke. If every running app used its whole budget, each would cost about 48 MB more than the ledger counts: 480 MB at ten apps, inside the 1 024 MB reserve; at about twenty-two apps the reserve alone would not cover it (an inference, not a measurement).
- **Why deferred:** changing it moves admission, the budget floor and the tests that pin them, so it waits for the owner's decision.
- **Done 2026-11-05:** the owner said to fix it. `OVERHEAD_PER_CHILD_MB` is now 64 (61.1 MB, the highest figure measured, rounded up to the next multiple of 16 MB), and design 5.7's worked example, its failure-table row and two contract examples carry the new arithmetic: ten apps of 512 MB commit 5 760 MB and leave 1 408 MB, an update of one beside its running release commits 6 336 MB and leaves 832 MB, and a 2 048 MB app is refused with `needs 2112 MB, 832 MB free`. `tests/unit/test_admission.py` pins that admission never counts less than the measured figure; the reconciler tests derive their limits from the constant. The 64 MB is one measurement on one container (Free Edition, four fixture kinds), not a limit the platform sets: a higher reading means raising the constant. The slot now holds fewer apps at their full budgets (at 512 MB each, 12 instead of 13 in a 7 168 MB ledger).
- **Seen again 2026-11-05 (in-order quickstart run):** with 64 MB charged per app, the ten apps of `test_capacity.py` cost 5 248 MB of the ledger. The dev App's six other apps held 2 560 MB and the default `memory_reserve_mb` is 1 024 MB, so 4 608 MB were free and the last node app was refused (`needs 832 MB, 192 MB free`). Admission was right; the test assumed room, and it now lowers the reserve for the run and restores it ([log](../specs/001-appmux-v1/spikes/README.md#sc-003-on-this-head-the-ledger-needed-room)). The same arithmetic applies to an operator: with the default reserve, ten 512 MB apps leave 1 408 MB, and the dev App's demos plus the T162 fixtures no longer fit together.
- **Trigger to fix:** met and done; the entry stays so the link from design 5.7 keeps working.
- **Created:** 2026-11-05
